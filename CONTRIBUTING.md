# Contributing

Спасибо за интерес к VK Social Commerce Prototyping Environment. Изменения должны быть небольшими, проверяемыми и опираться на подтверждённые источники.

## Основные правила

- Один PR решает одну понятную задачу.
- Для нетривиальной работы веди план в `tasks/todo.md`.
- Не заявляй готовность слоя, которого ещё нет в `docs/project-status.md`.
- Не добавляй официальные токены, компоненты, иконки, patterns или Figma keys без подтверждённого source of truth.
- Не смешивай архитектурную задачу с добавлением дизайн-системы без явной причины.
- Сохраняй смысловую эквивалентность `AGENTS.md` и `CLAUDE.md`.

## Типы изменений

| Изменение | Основная область | Обязательная проверка |
|---|---|---|
| Product documentation | `README.md`, `docs/` | Ссылки, актуальность статуса, отсутствие преждевременных обещаний |
| Agent adapters | `AGENTS.md`, `CLAUDE.md` | Semantic parity и корректные runtime-различия |
| Skills architecture | `.agents/README.md` | Progressive disclosure, ownership, discovery и size limits |
| Новый skill | `.agents/skills/<name>/` | Source of truth, frontmatter, trigger-тесты и `## @references` |
| UI foundations или components | Профильная директория после её утверждения | Source audit, сборка, accessibility и визуальная проверка |
| Showcase | `apps/showcase/` | `npm run lint` и `npm run build` |

## Workflow

1. Создай отдельную feature-ветку.
2. Зафиксируй план в `tasks/todo.md`, если задача нетривиальная.
3. Внеси только относящиеся к задаче изменения.
4. Проверь `git diff --check` и список файлов.
5. Выполни профильные тесты или сборку.
6. Обнови документацию и `docs/project-status.md`, если состояние проекта изменилось.
7. Сделай осмысленный коммит.
8. В PR опиши цель, изменения, источники, проверки и допущения.

## Работа с источниками VK

- Зафиксируй владельца и версию источника.
- Проверь права доступа и допустимый способ хранения ссылок.
- Не коммить access tokens, cookies и другие секреты.
- Не публикуй приватные внутренние ссылки без разрешения.
- При конфликте источников останови работу и запроси решение владельца.
- Любые временные значения помечай как допущения.

## Стиль документации

- Основной язык — русский.
- Технические идентификаторы, команды и пути пиши в `code`.
- Заголовки формулируй коротко, без точки в конце.
- Пиши действия и критерии проверки, а не общие обещания.
- Не дублируй большие справочники: ссылайся на один source of truth.

## Безопасность

- Не коммить `.env`, API keys и персональные credentials.
- Не используй реальные email и телефоны в примерах.
- Не публикуй приватные Figma file keys.
- Перед использованием материалов внутри VK отдельно проверь права и ограничения.

## Перед отправкой

```bash
git diff --check
git status --short
```

Для изменений showcase:

```bash
cd apps/showcase
npm run lint
npm run build
```
