# Архитектура skills

Документ задаёт общую конвенцию skills для Codex и Claude Code. Он описывает структуру, загрузку, зависимости и проверки, но не является источником продуктовых правил или дизайн-системы.

## 1. Reference и capability

Skills разделяются на два типа:

| Тип | Назначение | Содержимое |
|---|---|---|
| `reference` | Отвечает на вопрос «какие правила и данные относятся к теме» | Справочные правила, таблицы, определения, ограничения |
| `capability` | Отвечает на вопрос «как выполнить задачу» | Workflow, decision points, проверки и ссылки на reference skills |

Если skill в основном выполняет процесс, но использует большой справочник, он остаётся `capability`, а справочный контент выносится в reference skill или `references/`.

## 2. Структура skill

```text
.agents/skills/<skill-name>/
├── SKILL.md
└── references/
    ├── topic-a.md
    └── topic-b.md
```

- `SKILL.md` — entry point: назначение, обязательные правила, workflow и навигация.
- `references/` — тяжёлые справочники и подробные примеры, которые читаются только при необходимости.
- Каждый skill должен быть самодостаточной точкой входа по своей теме.

## 3. YAML frontmatter

Каждый `SKILL.md` начинается с YAML-блока:

```yaml
---
name: <skill-name>
description: <назначение, контекст использования и явные trigger-фразы>
type: reference
---
```

Требования:

- `name` совпадает с именем директории;
- `description` объясняет, когда skill нужно и не нужно использовать;
- `type` принимает значение `reference` или `capability`;
- frontmatter не должен заявлять возможности, которые ещё не реализованы.

## 4. Progressive disclosure

Runtime сначала читает metadata skills и загружает body только при совпадении запроса с `description`. Файлы из `references/` читаются по явной необходимости.

Чтобы lazy loading работал:

- оставляй в body только правила, необходимые для большинства задач;
- выноси большие каталоги, полные таблицы и длинные примеры в `references/`;
- добавляй точные ссылки на supporting files;
- не дублируй один справочник в нескольких skills.

## 5. Description и trigger-фразы

Хороший `description` содержит:

- назначение skill;
- тип задачи;
- явные русские и английские trigger-фразы;
- границы применения;
- отрицательную маршрутизацию, если skill легко спутать с соседним.

Не используй формулировки вида «для любых дизайн-задач»: они создают overreach и мешают точной маршрутизации.

## 6. `## @references`

Capability skill перечисляет reference skills в отдельной секции:

```markdown
## @references

- `example-components` — правила выбора компонентов
- `example-typography` — типографические ограничения
```

Reference skills не должны зависеть друг от друга напрямую. Если темы пересекаются, назначь одного владельца знания, а остальные связи проведи через capability layer.

## 7. Правило владельца темы

Для каждого правила, токена, компонента или паттерна должен существовать один source of truth.

- Владелец хранит полное определение.
- Остальные skills ссылаются на владельца и не копируют таблицы.
- Изменение темы начинается с обновления владельца.
- Конфликтующие определения блокируют завершение задачи до уточнения источника.

## 8. Naming

- Имена директорий и `name` используют lowercase kebab-case.
- Название отражает ответственность, а не конкретную задачу одного пользователя.
- Проектный префикс применяется только после утверждения области skill и подтверждения его источников.
- Будущий технический префикс проекта: `vk-commerce-`.

Наличие префикса само по себе не означает, что skill реализован или подтверждён.

## 9. Размер `SKILL.md`

- Hard limit: не более 500 строк.
- Soft target: 200–300 строк.
- При приближении к лимиту выноси справочники в `references/`, а не сжимай формулировки до потери смысла.
- Для supporting files длиннее 300 строк добавляй оглавление.

## 10. Императивная форма

Workflow и правила пиши как действия агента:

- «Проверь доступные источники»;
- «Определи состояние экрана»;
- «Перечисли допущения».

Избегай абстрактных описаний, из которых невозможно понять ожидаемое действие.

## 11. Доступ runtime

- Каноническая директория: `.agents/skills/`.
- Codex читает `.agents/skills/` напрямую.
- Claude Code использует symlink `.claude/skills` → `../.agents/skills`.
- `.claude/skills` не редактируется как отдельная копия.

Проверка symlink:

```bash
readlink .claude/skills
git ls-files --stage .claude/skills
```

Ожидаемый target — `../.agents/skills`, git mode — `120000`.

## 12. Discovery

End-to-end процесс:

1. Runtime сканирует YAML frontmatter.
2. Запрос сопоставляется с `description` и trigger-фразами.
3. Загружается подходящий `SKILL.md`.
4. Capability показывает доступные reference skills через `## @references`.
5. Агент читает только нужные supporting files.

Тестируй discovery в чистой сессии и фиксируй запрос, выбранный skill и фактически загруженные материалы.

## 13. Lifecycle

При добавлении или изменении skill:

1. Подтверди source of truth и область ответственности.
2. Выбери тип `reference` или `capability`.
3. Проверь naming и frontmatter.
4. Обнови `## @references`, если это capability.
5. Проверь размер файлов и отсутствие дублирования.
6. Проверь discovery на типовых и отрицательных запросах.
7. Выполни `git diff --check` и профильную валидацию.

## 14. Anti-patterns

- Дублирование справочника в нескольких skills.
- Reference → reference зависимости.
- Capability без ясного workflow.
- Общий `description` без trigger-фраз.
- Заявление о готовности неподтверждённых источников.
- Значения токенов, keys или компонентов без source of truth.
- `SKILL.md` длиннее 500 строк.
- Ручное расхождение между Codex и Claude.

## 15. Планирование и проверка

- Для нетривиальной задачи веди `tasks/todo.md`.
- Исправления пользователя фиксируй в `tasks/lessons.md`.
- Перед завершением проверяй diff, список файлов и фактический результат.
- Не объявляй готовность по плану: нужны свежие команды или иные проверяемые свидетельства.
